# Phase 1a: 純粋モジュール — statementReconciler / textPatch(アプリ非接続)

> 全体計画: `docs/overhaul/plan.md` を必ず先に読むこと。AGENTS.md の規則に従うこと。

## 目的

テキスト正準化の中核となる2つの純粋モジュールを、アプリに一切接続せずに
実装しテストで品質を確定する。ユーザー可視の挙動変更ゼロ。

1. **statementReconciler** — 再パース時に実行時要素IDを直前のコンパイル結果から
   最大限継承する照合器。
2. **textPatch** — モデル差分を「行スプライス」列に変換するパッチ生成器。

## 変更対象

* 新規 `src/document/statementReconciler.ts`
* 新規 `src/document/textPatch.ts`
* それぞれの `*.test.ts`
* (必要なら)`src/dsl/dslDocument.ts` の戻り値に文↔行対応情報を追加

## 設計仕様

### statementReconciler

入力: 旧コンパイル結果(実行時ID付き文+ソース行)、新パース結果。
出力: 新しい文へのID割当。

継承は以下の**優先順位付き6段階**で行う(2026-07-09 実装時にユーザー承認の上、
段階5「残余全体一意マッチ」を追加)。上位段階で対応付いた文は下位段階の対象から
除外する。判定は決定論的であること。

1. **LCS差分パス**: 新旧の文テキスト配列(トリム済み、コメント・空行除外)に
   LCS/Myers差分。不変領域の文は旧IDを直接継承。1行編集なら n−1 文が
   O(n) で解決する。
2. **完全キーマッチ**: 残余を「名前空間パス+名前+型」でペアリング。
   行内容が変わっても同一要素として扱う。**通常の属性編集**(名前・型不変)と
   **行移動**はここで対応付く。名前は同一スコープ内で一意(Phase 0 で同名は
   パーサエラー)なので、このマッチは曖昧にならない。
3. **位置対応ペアリング**: LCS差分の各**置換ハンク**(削除列と追加列が同じ
   位置で対向するもの)内で、残余の削除文と追加文を出現順にペアリングし、
   **型と名前空間パスが一致する**ペアはIDを継承する。**リネーム**
   (名前が変わったため段階2で対応付かない)と**無名⇄有名の遷移**
   (無名要素の命名・昇格)はここで同一要素と判定される。
4. **無名残余マッチ**: まだ残っている無名要素を「名前空間+型+残余内の
   相対順序」でペアリング。
5. **残余全体一意マッチ**: 残余の中で「名前+型」が新旧ちょうど1対1に対応する
   場合のみ継承(スコープ非依存)。**グループ跨ぎの移動**(indent/outdent)と
   **branch切替**(then⇄else)がここでID変化0になる。曖昧(同名同型が複数残る)
   なら継承しない。
6. 残りの追加は新規ID(既定 `createCadElementId`。純粋性とテスト再現性のため
   ID生成関数は options で注入可能とし、テストは決定論的生成器を渡す)、
   削除は消滅。

**リネームの判定規則(明文化)**: リネームは段階3で「同じ置換ハンク内・
同位置・同型・同名前空間」の削除/追加ペアとして同一要素と判定する。
**リネームと行移動を同一コミットで行った場合**は段階2(名前不一致)・
段階3(位置不一致)・段階5(名前不一致)のいずれも対応不能なため新規IDになる。
これは許容する設計制約(選択が外れるだけで文書の意味は正しい)としてテストで
固定する。**型の変更**も常に新規ID(型は全段階のマッチキー)。

### 期待するID継承結果(仕様表)

| 操作(1コミット内) | 対応付く段階 | ID変化数 |
|---|---|---|
| 属性編集(名前・型不変、位置不変) | 2(完全キー) | **0** |
| リネーム(位置・型不変) | 3(位置対応) | **0** |
| 行移動(内容不変) | 2(完全キー。LCS上は削除+挿入に見える) | **0** |
| 無名要素の属性編集(位置不変) | 3 または 4 | **0** |
| 無名要素の挿入 | 既存文は全て段階1、新文のみ段階6 | **1**(新規IDのみ、既存IDは全継承) |
| 無名要素の命名(自動昇格・手動) | 3(位置対応) | **0** |
| グループ跨ぎの移動(名前・型不変) | 5(残余全体一意) | **0** |
| branch切替(then⇄else) | 5(残余全体一意) | **0** |
| リネーム+行移動の同時実行 | 対応不能 | 1(許容制約) |
| 型の変更 | 対応不能 | 1 |

### textPatch

入力: 旧 `CompiledDocument`(statementMap: 要素ID→行範囲)、新旧要素配列の差分
(オブジェクト同一性で検出済み)、非要素フィールドの差分。
出力: `{startLine, endLine, replacementLines}[]` のスプライス列。

* 変更要素: その1文のみ再シリアライズして該当行を置換。
* 挿入: 配列順が示す位置に行挿入。グループ内への挿入は閉じ `}` 行の直前。
* 削除: 該当行除去。グループ削除は開き/閉じ行を除去しメンバーをアウトデント
  (現行の `selectionCommands` の削除セマンティクスに一致させる)。
* 移動・親変更: 削除+挿入として表現。
* 非要素(palette / roles / profiles / printLayouts / evaluationLimitIndex):
  各専用文セクションを同様にパッチ。`@stop` は移動=削除+挿入。

## 守るべき不変条件

* **両モジュールとも純粋関数**(Zustand・React・Tauri・グローバル状態に依存
  しない)。
* パッチはスプライスのみで表現し、対象外の行(コメント・空行・無関係な文)を
  絶対に変更しない。
* パッチ適用後のテキストは必ずパース可能(置換行はシリアライザ産のため
  構造的に保証されるが、テストで確認する)。
* 文書順を勝手に変えない。並べ替えは入力差分が明示した場合のみ。

## Phase開始時点の前提

* Phase 0 完了済み: ブロック構文・無名文・全文型・トークンスパン・
  `dslDocument.ts` ファサードが存在する。

## 完了条件

* 両モジュールがテストのみで検証され、アプリ本体からは未参照のまま
  マージ可能。
* `npm test` / `npm run build` / `npm run lint` 成功。

## 必須テスト

* **照合器(仕様表の全行をテスト化)**: 属性編集でID変化0/リネームで
  ID維持(段階3・位置対応)/行移動でID維持(段階2)/無名要素の属性編集で
  ID維持/無名要素の挿入で新規ID1・既存ID全継承/無名要素の命名(昇格)で
  ID維持/リネーム+移動同時で新規ID(許容制約の固定)/型変更で新規ID/
  グループ跨ぎの移動/全文置換。
* **照合器ストレス**: 1000文の文書で1行の属性編集 → **ID変化は0**
  (全ID継承)、実行 < 5ms。同条件でリネーム1件 → ID変化は0。
* **textPatch プロパティテスト**: ランダムな要素変更列(更新・挿入・削除・
  移動・グループ操作)を生成し、パッチ適用後テキストの `parse` 結果が期待
  モデルと意味的等価、かつ無関係行(挿入したコメント・空行)がバイト単位で
  不変であること。
* グループ挿入位置(`}` 直前)・グループ削除のアウトデント・`@stop` 移動の
  個別ケース。

## やってはいけないこと

* `cadDocumentStore` やコマンド・UIコンポーネントへの接続(それはPhase 1b/1c)。
* 「ファイル全体を再シリアライズ」するフォールバックの実装。部分パッチが
  表現できない差分があるなら、それはこのPhaseで解決すべき設計問題として扱う。
* ID生成方式(`src/model/cadIds.ts`)の変更。
* パフォーマンスのための投機的な複雑化(rope・インクリメンタルパーサ等)。
